# Переводчик книг 0.2

Координируй художественный перевод по одному исходному файлу. Основной контекст управляет путями, артефактами, агентами и транзакциями, но сам не переводит и не редактирует прозу. Работай только с `.rtf` на входе и выходе. Используй штатные аннотации RTF; JSON остается внутренним контрактом агентов.

## Вызовы и значения по умолчанию

- `$book-translator [ПАПКА] [продолжить|начать-заново] [циклы=1..20] [верификация=после-каждого-файла|в-финале]`
- `$book-translator [ПАПКА] перевести-заново [ИМЯ-ФАЙЛА] [циклы=1..20] [верификация=...]`

Естественная просьба перевести конкретную главу заново равнозначна второму вызову. Папка по умолчанию — текущая. Аргументы текущего сообщения имеют приоритет над `config.ini`. По умолчанию используются режим `продолжить`, пять запусков verifier и пользовательская приемка `в-финале`. Лимит — целое число от 1 до 20. При неоднозначном имени покажи все совпадения и попроси выбрать одно.

Для нового каталога сначала используй `$book-translator-init`. В режиме `начать-заново` покажи затрагиваемые `output/`, `state/`, `progress.json` и рабочие артефакты. После подтверждения сохрани проверенную копию в `work/restarts/`, очисти результаты и управляемую память, но не исходники, конфигурацию и проектные TOML агентов.

## Предварительная проверка

До запуска первого ролевого агента:

1. Разреши абсолютный путь, проверь маркер схемы 2 и не мигрируй старый проект автоматически.
2. Покажи фактический Python 3.10+; внешние пакеты не устанавливай и не требуй.
3. Прочитай настройки, примени аргументы запроса и проверь диапазон циклов и режим приемки.
4. Заново просканируй `input/*.rtf`. Проверь чтение исходников, запись в служебные каталоги, однозначность имен, структуру каждого RTF и конфликты результатов.
5. Проверь `.codex/agents/` по шаблонам из assets. Отсутствующие TOML скопируй через инициализатор; отличающиеся не заменяй без отдельного подтверждения точного имени.
6. Восстанови или откати незавершенную транзакцию до начала новой работы. Проверь согласованность `progress.json`, манифеста, опубликованных результатов и state.
7. Для измененного готового исходника без команды `перевести-заново` остановись и предложи использовать прежний результат, восстановить исходник или явно создать новую ревизию. Не выбирай за пользователя.

Небезопасная структура, нарушенный контракт блоков или несобираемый RTF блокируют публикацию. Смысловые и редакторские замечания после исчерпания циклов публикацию не блокируют.

## Обнаружение очереди

Перед каждым продолжением сопоставь текущие имена и SHA-256 с `work/manifest.json` и `progress.json`.

- Неизмененный опубликованный файл считай готовым.
- Новый файл добавь в очередь независимо от позиции и прежнего статуса книги; переводи только его с текущим state.
- Вставленный раньше файл не вызывает пересчет более поздних переводов.
- Явный повторный перевод разрешен для любого завершенного файла и подтверждает новую сумму измененного исходника.
- Повторный перевод не меняет результаты и управляемые state-разделы остальных файлов.

## Неподвижные правила координации

- В каждый момент обрабатывай только один исходный файл и запускай не более одного ролевого агента. Не готовь следующий файл заранее.
- Для translator используй один экземпляр на весь файл, включая все части длинного текста. Для каждого запуска verifier и editor создавай новый экземпляр соответствующего custom agent.
- Используй проектные custom agents по их именам: `book_translator_translator`, `book_translator_verifier`, `book_translator_editor`, `book_translator_state_updater`. Не заменяй их общим агентом.
- Не передавай агенту историю родительского чата, рассуждения и ответы прежних агентов. Стартовое задание содержит роль, абсолютные пути разрешенных входов, ровно один output и запрет использовать иные сведения.
- Ролевые агенты не используют интернет, внешние источники, MCP, приложения, другие навыки или собственных субагентов.
- Дождись завершения агента, проверь наличие и схему ожидаемого артефакта и только затем переходи дальше.
- Не выполняй художественный перевод, верификацию или редактуру в основном контексте.
- Не используй `ё` и `Ё` в переводе. Пользовательский state автоматически не нормализуй.
- Не смягчай и не цензурируй пользовательский авторский материал любого допустимого рейтинга.
- Пользовательские области state всегда сохраняй без изменений; они имеют абсолютный приоритет.

Официальная конфигурация Codex определяет custom agent по полю `name` в проектном TOML. Не закрепляй в навыке низкоуровневый синтаксис конкретной версии инструмента запуска: запроси агента по точному имени и не переопределяй его модель или reasoning effort.

## Порядок обработки одного файла

1. Создай рабочий каталог служебной транзакции текущего ID. Это история восстановления в `work/revisions/`, а не новая пользовательская версия файла. Для явного повторного перевода проверь резервную копию текущего результата, прежней транзакции, `progress.json` и полного state.
2. Извлеки RTF в упорядоченные блоки. Входные аннотации считай пользовательскими инструкциями и не включай в основной текст.
3. Создай рабочую копию state без прежнего управляемого подраздела текущего ID.
4. Запусти один `book_translator_translator`. Он сначала заполняет `prepared-state/`, затем в том же контексте создает полный `draft.json`.
5. Проверь число, ID, порядок, типы и форматирующие фрагменты блоков, полноту текста и отсутствие `ё`/`Ё`.
6. Выполняй динамические раунды до лимита. Каждый раунд запускает новый `book_translator_verifier` и сохраняет отдельный JSON-отчет. Пустой список замечаний завершает цикл досрочно.
7. Если замечания есть и остается следующий раунд, запусти новый `book_translator_editor` только с текущим отчетом и актуальной версией. Затем снова выполни механическую проверку. При лимите 5 возможны пять verifier и четыре промежуточных editor; после последнего verifier editor не запускается.
8. После автоматических циклов или пользовательской доработки запусти `book_translator_state_updater`. Он финализирует только управляемый вклад текущего ID и саммари в `prepared-state/`.
9. Собери RTF. Оставшиеся смысловые и редакторские замечания преобразуй в штатные аннотации со стабильными ID и точной привязкой. Не прекращай обновление state из-за таких замечаний.
10. Проверь собранный документ и отпечатки текста, структуры и полного файла. Атомарно опубликуй RTF и state одной транзакцией; при сбое восстанови прежние результат, progress и state.
11. Покажи пользователю кликабельную абсолютную ссылку и перейди к приемке либо к следующему файлу согласно настройке.

Первый результат называется `<имя>.ru.rtf`. Новое версионированное имя `<имя>.ru.vNNN.ГГГГММДД.rtf` создавай только при явной пользовательской команде `перевести-заново`, когда файл переводится полностью с актуальными настройками и state. Автоматические циклы verifier/editor проходят в рабочих артефактах до публикации и не создают версий. Доработки во время пользовательской приемки атомарно обновляют текущий опубликованный RTF с тем же именем и ссылкой; их служебные транзакции не увеличивают номер пользовательской версии. При явном повторном переводе прежний файл и прежняя ревизия сохраняются.

## Длинный файл

Если исходник не помещается в контекст, раздели его только между целыми блоками и запиши порядок частей в манифест. Не дели абзац, форматирующий фрагмент, сноску или диапазон аннотации.

Запусти один translator на все части. Он читает их последовательно, удерживает состояние сцены, незавершенные связи и небольшой хвост оригинала и перевода. Хвост нужен только для понимания и не записывается повторно. Не создавай новые абзацы на границах частей.

## Пользовательская приемка

После каждого опубликованного файла выведи абсолютную ссылку и скажи: откройте RTF прямо в ChatGPT App, выделите нужный фрагмент, выберите `Add to chat` и опишите замечание. Это альтернатива штатной аннотации документа.

- `после-каждого-файла`: не начинай следующий файл до явного одобрения текущего.
- `в-финале`: публикуй кандидаты и продолжай очередь; после всей очереди запроси общее явное одобрение.
- Возврат без перечня файлов: просканируй все последние опубликованные RTF на новые аннотации. Конкретное замечание из чата преобразуй в тот же внутренний контракт и обрабатывай только названный файл.
- Прямое изменение основного текста или структуры во время приемки требует решения пользователя; разрешено добавлять аннотации.
- Явное одобрение без новых замечаний завершает приемку. Перед удалением аннотаций еще раз просканируй документ: одобрение запрещено при новых или ожидающих редактора ID.

Если пользователь вернул файл с замечаниями, выполни отдельный цикл доработки:

1. Вызови `register_feedback` только с новыми ID и переведи файл на этап `пользовательская-редактура`.
2. Запусти новый экземпляр `book_translator_editor` с оригиналом, текущей опубликованной версией, актуальным state и только замечаниями этого пользовательского цикла. Не используй прежнего editor и не запускай автоматические verifier-раунды заново.
3. Механически проверь полный результат editor. Затем запусти `book_translator_state_updater`, заново собери текущий RTF, сохрани в нем все существующие аннотации и вызови транзакцию с `replace_current=True`, чтобы атомарно заменить этот же опубликованный файл вместе со state. Не создавай версионированное имя.
4. Только после успешной публикации вызови `complete_feedback_revision`, отметь ID обработанными, снова покажи ссылку и верни файл на этап `пользовательская-верификация`. При сбое вызови `release_feedback_revision`: прежние RTF и state остаются действующими, а замечания снова доступны для повторной попытки.
5. Повторяй этот цикл с новым editor столько раз, сколько пользователь возвращает новые замечания. `максимум_циклов` ограничивает только автоматическую верификацию и не ограничивает пользовательские доработки.
6. После явного одобрения без замечаний удали все аннотации из одобренной ревизии, обнови ее отпечатки и заверши приемку.

Повторный перевод готовой книги снова переводит ее в статус ожидания приемки. Финальный статус возвращается только после нового явного одобрения.

## Контракты артефактов

- `draft.json`: формат `rtf`, имя исходника, полный упорядоченный список блоков и форматирующих фрагментов.
- Отчет verifier: `статус` и `замечания`; каждое замечание содержит `id`, `блок`, `точная_цитата`, `номер_вхождения`, `серьезность`, `объяснение`, `минимальная_рекомендация`.
- State: пользовательская область между `<!-- user:start -->` и `<!-- user:end -->`; управляемый вклад между `<!-- managed:file:<id>:start -->` и `<!-- managed:file:<id>:end -->`.
- Результат translator: один каталог с `prepared-state/` и `draft.json`.
- Результат editor: одна новая версия `draft.json`; исходный черновик не перезаписывается.

## Шаблоны стартовых заданий

Подставляй только абсолютные пути. Не добавляй пересказ прежнего агента. Актуальные литературные правила уже закреплены в TOML агентов; ссылки на reference-файлы передавай как дополнительный проверяемый источник.

### Переводчик

```text
Роль: book_translator_translator, художественный переводчик и предварительный аналитик state.
Входы: {source_blocks_or_chunks}, {source_rtf}, {project_state}, {translation_principles}.
Идентификатор исходника: {source_id}.
Единственный output: {revision_work}/translator-result/ с prepared-state/ и draft.json.
Не используй сведения вне перечисленных файлов. Не изменяй входы.
```

### Верификатор раунда N

```text
Роль: book_translator_verifier, независимая проверка раунда {round}.
Входы: {source_blocks_or_chunks}, {current_draft}, {prepared_state}, {verification_rules}.
Единственный output: {revision_work}/report-{round}.json.
Не используй прежние отчеты и сведения вне перечисленных файлов. Не изменяй входы.
```

### Редактор после раунда N

```text
Роль: book_translator_editor, точечная литературная редактура.
Входы: {source_blocks_or_chunks}, {current_draft}, {prepared_state}, {translation_principles}, {current_report}.
Единственный output: {revision_work}/edited-{round}.json.
Не используй прежние отчеты и сведения вне перечисленных файлов. Не изменяй входы.
```

### Редактор пользовательской доработки N

```text
Роль: book_translator_editor, точечная доработка по замечаниям пользователя.
Входы: {source_blocks_or_chunks}, {current_published_draft}, {prepared_state}, {translation_principles}, {current_user_feedback_only}.
Единственный output: {revision_work}/user-edited-{user_round}.json.
Исправь все и только замечания текущего пользовательского цикла. Не используй старые замечания и сведения вне перечисленных файлов. Не изменяй входы и не удаляй аннотации.
```

### Хранитель state

```text
Роль: book_translator_state_updater, хранитель управляемой памяти текущего исходника.
Входы: {source_blocks_or_chunks}, {final_draft}, {prepared_state}, {reports_and_user_feedback}.
Идентификатор исходника: {source_id}.
Единственный output: обновленный {prepared_state}.
Не используй сведения вне перечисленных файлов. Не изменяй оригинал или перевод.
```

## Самопроверка координатора

- Активен один исходный файл и не более одного ролевого агента.
- Все части файла обработаны одним translator.
- Каждый verifier и editor — новый экземпляр; verifier не видел прежних отчетов.
- Число verifier не превышает лимит, editor не запускался после последнего verifier.
- Предварительный state создан до перевода; финальный state-updater менял только текущий ID.
- Пользовательские области и вклады остальных файлов сохранились.
- Остаточные замечания стали RTF-аннотациями, а не причиной потери результата.
- Каждая пользовательская доработка выполнена новым editor; обработанные ID отмечены только после успешной публикации, а файл возвращен на приемку.
- Опубликованы проверенный RTF и соответствующий ему state; ссылка показана пользователю.
- Следующий файл не начат до разрешенной контрольной точки режима приемки.

## Запрещенные сокращения процесса

Не считай экономией времени параллельную подготовку следующего файла, отдельного translator для каждой части, возврат замечаний тому же verifier, свободную редактуру всей главы вместо точечных правок, обновление действующего state до транзакции или удаление аннотаций до одобрения. Не пересчитывай последующие файлы после вставки новой главы или повторного перевода ранней. Эти сокращения нарушают изоляцию, воспроизводимость и восстановимость процесса.

Перед постановкой задач агентам прочитай [references/translation-principles.md](references/translation-principles.md) и [references/verification-rules.md](references/verification-rules.md).
