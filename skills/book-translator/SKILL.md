# Book Translator 0.2

Работай только с `.rtf` на входе и выходе. Используй штатные аннотации RTF. JSON — внутренний контракт между агентами и не является пользовательским форматом.

## Вызовы

- `$book-translator [ПАПКА] [продолжить|начать-заново] [циклы=1..20] [верификация=после-каждого-файла|в-финале]`
- `$book-translator [ПАПКА] перевести-заново [ИМЯ-ФАЙЛА] [циклы=1..20] [верификация=...]`

Естественная просьба перевести конкретную главу заново равнозначна второму вызову. Аргументы сообщения имеют приоритет над `config.ini`. По умолчанию: `продолжить`, пять запусков verifier, пользовательская приемка `в-финале`. При неоднозначном имени покажи совпадения и попроси выбрать одно. Для нового каталога сначала используй `$book-translator-init`.

В режиме `начать-заново` сначала покажи затрагиваемые `output/`, `state/`, `progress.json` и рабочие артефакты. После подтверждения вызови безопасный перезапуск: он сохраняет проверенную копию в `work/restarts/`, очищает результаты и управляемую память и создает состояние схемы 2 заново. Конфигурация и проектные TOML агентов сохраняются.

## Непреложные ограничения

1. До любого запуска проверь маркер схемы, конфигурацию, RTF и восстановимость проекта. Небезопасная структура RTF или несобираемый результат блокируют публикацию; замечания о переводе не блокируют ее.
2. Не изменяй входные RTF. Все их аннотации — пользовательские инструкции, не основной текст.
3. Не используй `ё` и `Ё` в переводе. Механическая проверка и verifier считают их ошибкой. Пользовательский state автоматически не нормализуй.
4. Все агенты точно преобразуют предоставленный пользователем авторский материал и не создают самостоятельную сцену. Поэтому они не смягчают и не цензурируют допустимые сцены любого рейтинга, включая секс, насилие, кровь, жестокость, зависимость, травму и иную взрослую тематику.
5. Пользовательские области state имеют абсолютный приоритет и всегда сохраняются.

## Обнаружение очереди

Перед каждым продолжением заново просканируй `input/*.rtf` и сопоставь имена и SHA-256 с `work/manifest.json` и `progress.json`.

- Неизмененный опубликованный файл готов.
- Новый файл добавь в очередь независимо от позиции и от прежнего статуса книги. Переводи только его с актуальным state; готовые более поздние файлы не пересчитывай.
- Измененный готовый исходник без явного `перевести-заново` требует решения пользователя.
- При явном повторном переводе обновленный исходник разрешен и его новая сумма фиксируется.
- Повторный перевод не меняет переводы и управляемые state-разделы остальных файлов.

## Обработка одного файла

1. Создай рабочий каталог ревизии. Для повторного перевода предварительно сделай проверенную резервную копию текущего результата, прежних артефактов, `progress.json` и полного state в `work/revisions/<id>/<ревизия>/`.
2. Создай рабочую копию state без прежнего управляемого подраздела текущего ID.
3. Запусти один экземпляр `book_translator_translator`. Он сначала анализирует весь оригинал, аннотации и актуальный state; до перевода заполняет `prepared-state/` точкой зрения частей, голосами рассказчика и персонажей, отношениями, эмоциональным подтекстом, намеренными повторами, паузами, обрывами, темпом, ритмом и контекстными значениями терминов мира; затем в том же контексте создает `draft.json`.
4. Проведи механическую проверку полноты блоков, структуры и запрета `ё`.
5. Выполняй динамические раунды до лимита. Каждый раунд — новый `book_translator_verifier`. Если замечаний нет, заверши досрочно. Если замечания есть и остается следующий раунд, новый `book_translator_editor` исправляет только отмеченные фрагменты. При лимите 5 возможны пять отчетов verifier и четыре промежуточных редактора. JSON-отчеты сохраняй в ревизии.
6. После последнего раунда запусти `book_translator_state_updater`: он заменяет только управляемый вклад текущего ID и его саммари.
7. Собери RTF. Если замечания остались, добавь каждое как штатную RTF-аннотацию к точной цитате. Не останавливай дальнейшую работу из-за этих замечаний.
8. Еще раз проверь сборку. Атомарно опубликуй RTF и подготовленный state одной транзакцией. При сбое восстанови предыдущий перевод, progress и state.

Первый результат называется `<имя>.ru.rtf`. Повторный перевод создает рядом новый файл `<имя>.ru.vNNN.ГГГГММДД.rtf` только после успешной сборки; прежний файл сохраняется как история. Он получает новый номер ревизии и не конфликтует с первоначальной транзакцией.

## Пользовательская приемка

После каждого опубликованного файла обязательно выведи кликабельную абсолютную ссылку. Скажи: откройте RTF прямо в ChatGPT App; выделите нужный фрагмент, выберите `Add to chat` и опишите замечание. Это альтернатива штатной аннотации в документе.

- `после-каждого-файла`: не начинай следующий файл до явного одобрения текущего.
- `в-финале`: публикуй каждый кандидат сразу и продолжай очередь; после всех файлов запроси общее явное одобрение.
- Возврат «на доработку» без списка файлов: просканируй все опубликованные RTF на новые аннотации.
- Конкретное замечание из чата: преобразуй его в тот же внутренний контракт пользовательской аннотации и обработай только указанный файл.
- Различай изменения по отдельным хешам текста, структуры и полного файла. Во время приемки разрешено только добавлять аннотации; прямая правка основного текста требует решения пользователя.
- Обработанные ID запиши в журнал, не применяй повторно. Комментарии остаются видимыми после исправления. Удали все аннотации только после явного одобрения пользователя, затем обнови хеш результата.

При повторном переводе уже готовая книга вновь ожидает пользовательского одобрения. Финальный статус возвращается только после нового явного одобрения.

## Контракты файлов

- `draft.json`: `формат: rtf`, исходный файл, полный упорядоченный список блоков и фрагментов.
- Отчет verifier: статус и замечания со стабильными `id`, `блок`, `точная_цитата`, `номер_вхождения`, `серьезность`, `объяснение`, `минимальная_рекомендация`.
- State: пользовательская область между `<!-- user:start -->` и `<!-- user:end -->`; управляемые вклады между маркерами `<!-- managed:file:<id>:start -->` и `<!-- managed:file:<id>:end -->`.

Подробные литературные критерии обязательны для translator, verifier и editor: прочитай [references/translation-principles.md](references/translation-principles.md) и [references/verification-rules.md](references/verification-rules.md) перед постановкой задач агентам.
