# Руководство по репозиторию

## Структура проекта

Репозиторий содержит два навыка Codex для перевода книг в формате RTF.

- `skills/book-translator/` — основной процесс, Python-скрипты, литературные правила, шаблоны state и TOML агентов.
- `skills/book-translator-init/` — инициализация рабочего каталога.
- `hooks/` — stop hook и его JSON-регистрация.
- `tests/` — модульные, контрактные, hook- и сквозные тесты.
- `.codex-plugin/plugin.json` — манифест плагина; `README.md` — пользовательское руководство.

Исполняемый код размещайте в `skills/book-translator/scripts/`. Файлы, копируемые в пользовательский проект, храните в `assets/`, а не в корне репозитория.

## Команды разработки и проверки

Требуется Python 3.10+. Внешних зависимостей и отдельного этапа сборки нет.

```powershell
py -3 -B -m unittest discover -s tests -v
py -3 -B skills/book-translator/scripts/init-project.py --help
git diff --check
```

Первая команда запускает все тесты без создания байткода, вторая проверяет CLI инициализатора, третья находит ошибки пробелов и окончаний строк.

## Стиль кода и именование

Используйте отступы в четыре пробела, UTF-8, аннотации типов, `pathlib.Path` и стандартную библиотеку. Функции и переменные именуйте в `snake_case`, тестовые классы — в `PascalCase`, тесты — `test_<поведение>`. Пользовательские контракты и ключи state пишите по-русски; внутренние Python-идентификаторы должны быть краткими и понятными.

Сохраняйте атомарность записи: временный файл рядом с целью, проверка, затем замена. Не ослабляйте защиту путей и ссылок, проверку структуры RTF, стабильность ID аннотаций и откат транзакций. Перевод должен отклонять `ё` и `Ё`; пользовательский state изменять автоматически нельзя.

## Язык документации

Все README, инструкции навыков, справочные материалы, примеры конфигурации и пользовательские сообщения должны быть на русском языке. Английский допустим только для имен API, команд, форматов и терминов, не имеющих устойчивого русского эквивалента. При изменении поведения одновременно обновляйте соответствующую документацию.

## Требования к тестам

Используется `unittest`. Тесты должны быть детерминированными, автономными и работать во временных каталогах. Изменения парсера сопровождайте точечными RTF-тестами, изменения процесса — сквозным регрессионным сценарием. Проверяйте успешный путь и откат. Фикстуры должны быть нейтральными; прежние примеры разрешены только как хеши denylist.

## Коммиты и pull request

История использует префиксы `feat:`, `fix:` и `docs:` с коротким повелительным описанием на русском. Один коммит должен решать одну задачу.

В pull request опишите пользовательские изменения, совместимость, влияние на state/манифест и откат. Укажите команду и результат тестов, привяжите задачу при наличии. При изменении контрактов обновляйте `README.md`, инструкции навыков, assets и тесты вместе.
